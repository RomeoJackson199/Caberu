# Encryption Review

**Date:** 2026-02-06
**Scope:** All encryption, key management, and cryptographic implementations in the Caberu codebase

---

## Executive Summary

The application implements database-level encryption for PHI (Protected Health Information) using PostgreSQL's pgcrypto extension with PGP symmetric encryption, backed by Supabase Vault for key management. The overall architecture is sound for a healthcare application targeting HIPAA/GDPR compliance, but there are several issues ranging from critical to informational that should be addressed.

---

## Critical Issues

### 1. Hardcoded Encryption Key in Migration History

**File:** `supabase/migrations/20251210_implement_encryption_trigger.sql:15`

```sql
RETURN 'base64:J9/8v7s2+1w4/L0k1+2s9+5y4/P23+0='; -- Example fixed key
```

The `private.get_app_key()` function contains a hardcoded encryption key. While later migrations introduce `private.get_encryption_key()` which reads from Supabase Vault, the old `get_app_key()` function is **still referenced** by `encrypt_treatment_plan_trigger()` (see `20260205090000_fix_encryption_function_search_path.sql:399`). This means the legacy trigger for treatment plans may still use the hardcoded key rather than the Vault-managed key.

**Risk:** If the legacy trigger fires, data is encrypted with a key visible in migration source code. Anyone with access to the repo can decrypt that data.

**Recommendation:** Remove `private.get_app_key()` entirely and ensure all triggers exclusively use `private.get_encryption_key()`.

### 2. Dual/Conflicting Trigger Functions for Treatment Plans

There are two separate trigger functions for treatment plans:
- `encrypt_treatment_plan_trigger()` — uses `private.get_app_key()` (hardcoded key), NULLs out plaintext
- `encrypt_treatment_plans_phi()` — uses `private.get_encryption_key()` (Vault key), NULLs out plaintext

If both triggers are bound to the same table, data may be double-encrypted or encrypted with different keys, making decryption unreliable. The migration history does not clearly show that the legacy trigger (`trg_encrypt_treatment_plan`) was dropped before the new one was added.

**Recommendation:** Explicitly `DROP TRIGGER IF EXISTS trg_encrypt_treatment_plan` in the latest enforcement migration, and drop the `encrypt_treatment_plan_trigger()` function.

### 3. Plaintext Cleared Even When No Encryption Key Available

In `20260215000001_enforce_phi_encryption_only.sql`, when `enc_key IS NULL OR enc_key = ''`, the triggers still set plaintext fields to `NULL`:

```sql
IF enc_key IS NULL OR enc_key = '' THEN
    NEW.reason := NULL;
    NEW.notes := NULL;
    ...
    RETURN NEW;
END IF;
```

This means if the Vault key is not configured (e.g., during development, migration, or key rotation failure), **all PHI data is silently destroyed on write** — neither encrypted nor stored in plaintext.

**Risk:** Data loss during key unavailability. This is a silent, catastrophic failure mode.

**Recommendation:** When the key is unavailable, either: (a) raise an exception to reject the write, or (b) allow plaintext storage and log a critical alert. Option (a) is safer for production; option (b) is acceptable for dev environments only.

## High Severity Issues

### 4. 2FA Verification Codes Stored in Plaintext

**File:** `supabase/functions/send-2fa-code/index.ts:74`

The 6-digit verification code is stored as plaintext in the `verification_codes` table:

```typescript
.insert({ email, code, type, expires_at, used: false, failed_attempts: 0 })
```

Anyone with database read access (admin, backup, SQL injection) can read active 2FA codes and bypass authentication.

**Recommendation:** Hash the code before storage (e.g., SHA-256) and compare hashes during verification. The code is short-lived and numeric, so a fast hash is acceptable here.

### 5. Weak 2FA Code Generation Using `Math.random()`

**File:** `supabase/functions/send-2fa-code/index.ts:52`

```typescript
const code = Math.floor(100000 + Math.random() * 900000).toString();
```

`Math.random()` is not cryptographically secure. In V8-based environments (Deno), the output is generated by a PRNG (xorshift128+) that is predictable if the internal state is known.

**Recommendation:** Use `crypto.getRandomValues()` for code generation:
```typescript
const array = new Uint32Array(1);
crypto.getRandomValues(array);
const code = (100000 + (array[0] % 900000)).toString();
```

### 6. PGP Symmetric Encryption Without Cipher Options

All encryption calls use the default `pgp_sym_encrypt(data, key)` without specifying cipher algorithm, compression, or integrity options:

```sql
pgp_sym_encrypt(NEW.reason, enc_key)
```

The default pgcrypto cipher for PGP symmetric encryption is AES-128 with SHA-1 for integrity. While AES-128 is currently adequate, SHA-1 is deprecated for integrity purposes.

**Recommendation:** Explicitly specify cipher options:
```sql
pgp_sym_encrypt(NEW.reason, enc_key, 'cipher-algo=aes256, compress-algo=0')
```

### 7. Inconsistent Password Minimum Length Requirements

Two separate password validators exist with conflicting requirements:

- `src/utils/passwordValidation.ts:21` — requires **12 characters minimum**
- `src/lib/security.ts:49` — requires **8 characters minimum**

**Recommendation:** Consolidate to a single password validation module. The 12-character minimum is the correct standard for HIPAA-adjacent applications.

## Medium Severity Issues

### 8. CSRF Validation Bypassed for Requests Without Origin/Referer

**File:** `supabase/functions/_shared/csrf.ts:36`

```typescript
console.warn('CSRF: Request without Origin or Referer header');
return { isValid: true }; // Be permissive for now, log for monitoring
```

Requests without an `Origin` or `Referer` header are allowed through. While the comment says "for now," this effectively disables CSRF protection for any request that strips these headers (e.g., curl, Postman, or custom HTTP clients).

**Recommendation:** Reject requests without origin/referer unless they carry a valid service role key. The current service_role check at line 30 only checks if the auth header *includes* the string `service_role`, which is a weak check — an attacker could craft an Authorization header containing that string.

### 9. Client-Side SQL Injection "Protection" is Misleading

**File:** `src/lib/security.ts:17-23`

```typescript
export const sanitizeInput = (input: string): string => {
  return input
    .replace(/['";\\]/g, '')
    .replace(/(-{2}|\/\*|\*\/|xp_|sp_)/gi, '')
    .trim();
};
```

Client-side SQL sanitization provides no real protection since it can be bypassed entirely. If this function creates a false sense of security and is relied upon in place of parameterized queries, it's a vulnerability.

**Recommendation:** Remove this function or clearly document it as a cosmetic/UX measure only. Ensure all database queries use parameterized queries (which Supabase's JS client does by default).

### 10. Decrypted Views Granted to All `authenticated` Users

All decrypted views (`v_appointments_decrypted`, `v_notes_decrypted`, etc.) are granted `SELECT` access to the `authenticated` role:

```sql
GRANT SELECT ON public.v_appointments_decrypted TO authenticated;
```

This means any authenticated user (patient, staff, admin) can potentially read decrypted PHI for all rows, unless Row-Level Security (RLS) policies are applied to the underlying tables and propagate through the views.

**Note:** PostgreSQL views evaluate RLS based on the view definer's permissions when `SECURITY DEFINER` is used in the underlying functions. Verify that RLS policies on the base tables are enforced when querying through these views.

### 11. No Key Rotation Strategy

The system uses a single encryption key from Supabase Vault (`app_encryption_key`). There is no evidence of:
- Key versioning or key ID tracking per encrypted record
- A key rotation procedure
- Re-encryption tooling for existing data

If the key is ever compromised, all historical data encrypted with that key is exposed, and there's no mechanism to rotate to a new key without manual re-encryption of every encrypted field.

**Recommendation:** Add a `key_version` column to encrypted tables, and build a re-encryption migration tool.

## Low Severity / Informational

### 12. `search_path` Inconsistency Across Functions

Some functions use `SET search_path = 'public, extensions'` while others use `SET search_path TO 'public'`. The inconsistency means some functions may fail to find `pgp_sym_encrypt` if the extension is installed in the `extensions` schema, while others will work. The later migration (`20260205090000`) correctly prefixes with `extensions.pgp_sym_encrypt()`, making the search_path less critical, but the inconsistency should be cleaned up.

### 13. `get_encryption_key()` Fails Open

**File:** Based on exploration, `private.get_encryption_key()` returns NULL when the Vault secret is not found, allowing triggers to skip encryption silently.

For a healthcare application, "fail open" (allow unencrypted data) is a dangerous default. Consider failing closed (rejecting the write) in production environments.

### 14. Password Breach Check Fails Open

**File:** `src/utils/passwordValidation.ts:107-108`

```typescript
if (!response.ok) {
    console.warn('HIBP API unavailable');
    return false; // Don't block user if API fails
}
```

If the HIBP API is unavailable, breached passwords are accepted. This is a reasonable UX tradeoff but should be logged as a security event, not just a console warning.

### 15. Session Storage for Business ID

`selected_business_id` is stored in `sessionStorage`. While sessionStorage is more secure than localStorage (cleared on tab close), it's still accessible to XSS. For a multi-tenant healthcare application, business context tampering could allow cross-tenant data access if not validated server-side.

**Recommendation:** Always validate business membership server-side. Never trust client-side business ID selection for authorization.

## Positive Findings

1. **Vault-based key management** — Production encryption keys are stored in Supabase Vault, not in code (except the legacy `get_app_key` issue noted above)
2. **Trigger-based encryption** — Transparent encryption on INSERT/UPDATE ensures the application layer doesn't need to manage encryption directly
3. **Plaintext NULLing** — The latest triggers clear plaintext after encryption, ensuring PHI is only stored in encrypted form
4. **Decryption fallback** — `get_decrypted_or_plain()` handles the migration period where some data may be pre-encryption
5. **HIBP integration** — Password breach checking with k-anonymity is a strong pattern
6. **Rate limiting on auth endpoints** — Login, 2FA, and password reset all have rate limiting
7. **SECURITY DEFINER with SET search_path** — Functions use security definer correctly with immutable search paths to prevent privilege escalation
8. **Session timeout compliance** — 15-minute session timeout for GDPR compliance
9. **Comprehensive PHI coverage** — 14+ tables have encryption triggers for sensitive fields
